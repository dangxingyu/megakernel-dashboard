2同一张卡、同一个客户端的对比The comparison on one card with one client

“Agent 的进度”一节里的 engine 是在自己的进程里计时的，baseline 是经 HTTP 由客户端计时的，两者不能直接相比。这里把我们的 engine 也放到一个 OpenAI 兼容的流式 HTTP 服务后面（eval/serve_engine.py：前端进程 + engine 进程，每个 token 一个 SSE chunk，增量 detokenize），然后在同一张 H100 上让各系统轮流起服务，用同一个客户端测稳态 decode（prompt 64，生成 1024，greedy）。每轮每个系统重新启动，每轮换起始顺序；每次启动先热身 1 次再测 3 次。

The engines in the section on the agent's progress are timed inside their own process and the baselines over HTTP on the client's clock, so the two are not comparable as they stand. Here our engine also sits behind an OpenAI-compatible streaming HTTP server (eval/serve_engine.py: a front-end process and an engine process, one SSE chunk per token, incremental detokenization), and on one H100 the systems are served in turn and measured by the same client on steady decode (prompt 64, 1024 new tokens, greedy). Every round restarts every server and begins with a different system; each start has one warm-up repeat and three measured ones.

结果分两条线报。A 线（对齐）：同一个模型，权重格式、activation 的数值格式和数据流都和通用 engine 一样，是苹果对苹果的比较。B 线（模型专用）：允许无损地换格式，例如把 BF16 权重无损地存成 12 bit、在 kernel 里解码。两条线并排报，不混在一起。

Results are reported on two tracks. Track A (aligned): the same model with the weight format, the number format of the activations and the data flow of the general engines: apples to apples. Track B (model-specific): lossless changes of format are allowed, for example BF16 weights stored losslessly in 12 bits and decoded inside the kernel. The two are shown side by side and never mixed.

Workload 和计时Workload and timing

稳态 decode。B 条流同时开始（B = 1、8），每条 prompt 64 个 token，生成 1024 个新 token（忽略 EOS），greedy。先 warm-up 一次，再重复 5 次；图里的点是中位数，横杠是 min–max。

Steady decode. B streams start together (B = 1, 8), each with a 64-token prompt, generating 1024 new tokens (EOS ignored), greedy. One warm-up, then 5 repeats; a marker is the median and its bar the min–max.

计时全部在 client 端，单调时钟，走 HTTP 流式接口：server 自己报的速度一律不用。“decode tok/s”= 所有流都在 decode 的那段窗口里到达的 token 数除以窗口长度；“每步时间”= 1000·B / tok/s；“token 间隔”是同一条流相邻两个 token 的到达间隔。

All timing is on the client, monotonic clock, through the streaming HTTP API: nothing a server reports about its own speed is used. “Decode tok/s” = tokens that arrive while every stream is decoding, divided by that window; “time per step” = 1000·B / tok/s; a “token gap” is the time between consecutive tokens of one stream.

GPU 空闲（host gap）怎么量。同一个 server 在 Nsight Systems（nsys）下再启动一次，CUDA graph 按节点 trace（按整图 trace 时图里的 kernel 不留记录，GPU 看起来几乎全空闲：第一次试跑就这么错了）。trace 一次重复，取中间 80% 的时间，把 CUPTI 记录的 kernel 执行区间合并；区间之间的时间就是 GPU 没在跑任何 kernel、在等 host 的时间。三个量：空闲占比 = 空闲时间 / 窗口；每步空闲 µs = 空闲占比 × 该次重复的 token 间隔中位数；每步 ≥ 20 µs 的间隙数：长到像一次 host 往返、而不是两个 kernel 首尾相接的间隙。trace 本身会拖慢 host，所以这些是上界，表里给出带 trace 时慢了多少。

How GPU idle (the host gap) is measured. The same server is launched again under Nsight Systems (nsys) with CUDA graphs traced per node (traced as whole graphs, the kernels inside a graph leave no record and the GPU looks almost entirely idle: the first trial made that mistake). One repeat is traced; over the middle 80% of it the kernel execution intervals recorded by CUPTI are merged, and the time between merged intervals is time in which the GPU ran no kernel and waited for the host. Three quantities: idle share = idle time / window; idle µs per step = idle share × that repeat's median token gap; gaps ≥ 20 µs per step: gaps long enough to be a host round trip rather than back-to-back launches. Tracing slows the host, so these are upper bounds; the tables say how much slower the traced repeat was.
